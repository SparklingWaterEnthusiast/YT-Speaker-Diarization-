# YTScribe v0.3.0 — measured optimization report

September 19, 2026. **MEASURED** means observed here; **REPORTED** means historical
or user-supplied; **INFERRED** means an interpretation; **UNVERIFIED** means not
established. Hardware advice separately distinguishes research from estimates.
Machine-readable evidence: [summary](results/v0.3.0-summary.json),
[timestamp proxies](results/timestamp-proxies.json). Raw run directories remain
locally available but are ignored by Git because they contain large traces/audio.

## 1. Executive Result

Implemented the optimization overhaul without replacing the existing models,
speaker recognition, queue tabs or stage architecture. The main speed bottleneck
was sequential ASR execution; the main stability/performance defect reproduced
was excessive newly-created PyTorch reservation after a diarization-first restart.

Optional batch-4 transcription cut warm ASR from **205.401 to 63.928 seconds**
against the frozen-source recheck: **68.88% less time / 3.21× throughput** on the
same 1706.202-second source. The initial baseline was 210.785 s warm and 230.208 s
cold inference. These are ASR times, not download-to-export times. Sequential
large-v3/beam 5/word timestamps remain the accuracy-oriented default.

The real Qt pause/close/relaunch test passed, followed by a three-item queue.
A separate final cold-model Qt run processed the full source from cached WAV
through Markdown export in **136.271 s (12.52× realtime)**, including model
initialization and worker shutdown. Download and window construction are excluded.
A physical-memory-aware allocator limit reduced the first resumed diarization
stage **103.344 → 20.922 s** (79.75% less time), without changing its speaker
boundaries. A deliberately restricted real GPU run also recovered from OOM at
batch 32 by retrying at 16. No production queue/profile/output data was changed.

## 3. Original Anomalies

### 4–6× realtime performance — PARTIAL

**Evidence:** initial measured ML-stage sum including model loads was 311.091 s,
or **5.485× realtime**; warm ASR+diarization was 258.923 s, **6.590×**. ASR alone
was faster: 7.412× cold inference and 8.094× warm. The later frozen-source recheck
was 8.511×/8.307× ASR. No exact reproduction of every reported 4× run is claimed.

**Root cause:** timing denominator, serial ASR work, model initialization and
laptop conditions explain substantial variation. A separate restart pathology
can depress performance further. **Fix/result:** optional batching and lifecycle
corrections; see the measured table below. Historical configuration drift or a
specific older-version regression remains unverified.

### Approximately 50% GPU utilization — CONFIRMED

**Evidence:** initial ASR averages 49.80%/45.97%; recheck 51.05%/51.90%, with
individual samples ranging from a few percent to 100%. Process CPU averaged
roughly 1–2 core-equivalents during original ASR; low overall CPU usage did not
exclude serial work. **Root cause (INFERRED):** single-chunk autoregressive
decoding and host/decoder coordination leave GPU capacity unused; utilization
alone cannot prove a single CPU or GPU kernel bottleneck. **Fix/result:** batch 4
raised measured ASR averages to ~68%, with much shorter runtime. No GPU concurrency
was needed. Near-100% diarization is normal when throughput and memory are healthy.

### Historical 5.3× versus 10–15× — PARTIAL

**Evidence:** the REPORTED 5.3× cold historical record is consistent with the
initial 5.485× measured ML-stage sum. The old 10–15× bulk claim had no comparable
trace/methodology and was removed as a guarantee. Removing initialization alone
does not turn 5.3× into 10–15×. **Root cause:** mixed timing boundaries and an
unsupported sustained estimate; unknown past power/configuration differences.
**Fix/result:** measured stages and cold/warm labels replace blanket estimates.
The new batch mode can reach those ranges here; that does not validate old claims.
GTX 1060 Laptop 6 GB at ~4× remains strictly USER-REPORTED, not benchmarked.

### Restart → diarization → next item — CONFIRMED pathology, fixed in tested workflow

**Evidence:** exited process 19176 was replaced by process 14292. The fresh process
created a PyTorch peak allocation of 9,432,108,032 bytes and reservation of
11,374,952,448 bytes on the physical 8 GiB GPU. First-item diarization took 103.344 s;
the next ASR slowed while unused torch reservation remained. This degraded diagnostic
was intentionally terminated, not counted as a successful endurance run.

**Root cause (INFERRED):** workspace/allocator behavior plus Windows system-memory
fallback, not objects surviving process exit. Exact cuDNN algorithm selection and
physical page migration were not traced. [NVIDIA documents fallback and its speed cost](https://nvidia.custhelp.com/app/answers/detail/a_id/5490/kw/support).
**Fix/result:** constrain the PyTorch allocator using physical free VRAM and release
unused torch scratch cache before CT2 work; the corrected fresh-process workflow
completed with ~2.108 GB peak reservation and no duplicated models.

## 7. GPU Memory Lifecycle

ASR and diarization load lazily only when needed. Keep mode retains weights;
stage mode unloads the other framework's model before an uncached stage. All
models/prefetch ownership is released at run completion. CT2 and torch have
separate pools; torch counters cannot explain all driver VRAM.

The temporary torch budget is `NVML_free + torch_reserved - configured_margin`,
bounded below by live tensor bytes and above by an existing stricter allocator
fraction. This prevents the measured uncontrolled scratch reservation, but is
not a bound on CT2, driver/context allocations, other processes or weight loading.
[PyTorch allocator limit](https://docs.pytorch.org/docs/main/generated/torch.cuda.memory.set_per_process_memory_fraction.html),
[cache semantics](https://docs.pytorch.org/docs/2.12/notes/cuda.html#memory-management).

Corrected lifecycle receipts: actual interpreter PID **8516** transcribed then
paused/closed; new interpreter PID **18760** reused ASR and loaded diarization
first. ASR was loaded once only when the next item needed it. Windows venv launcher
PIDs in the external monitor are 18856/8640, distinct from interpreter PIDs.
Driver VRAM was 767 MiB before initial launch, ~815 MiB before relaunch, and
~740 MiB after final exit. This background occupancy is not a YTScribe leak.

Three resumed item peaks: **3012/4939/4937 MiB VRAM**, **1927/4810/2600 MiB RSS**;
thread counts at item ends **64/66/66**, reflecting runtime initialization, not
one new worker per item. No sustained growth was observed over this bounded test.
PyTorch peak allocated/reserved were **1.708/2.108 decimal GB**. Higher residency
and allocator reservation are not automatically leaks; no surviving cross-process
allocation or duplicate model ownership was found. A multi-day leak is not ruled
out by three excerpts.

## 8. Optimization Control Panel

Settings includes an explicit asynchronous hardware probe; GPU/VRAM, runtime
precision support, compute capability, CPU cores and RAM are shown. Unknown form
factor is displayed as unknown rather than inferred from power/VRAM. Normal UI
opening/resource sampling does not initialize CUDA; explicit probing may do so.

Safe uses sequential ASR and stage residency; Balanced retains the sequential
accuracy baseline with model reuse; Performance explicitly selects batch 4.
All keep large-v3, beam 5, words/VAD and one GPU job. Presets require Apply and
never silently overwrite saved settings on upgrade. ≤6 GiB capability input favors
stage residency. Controls include model, supported precision, language, beam,
batch/chunk/CPU threads, speaker bounds, diarization batch, memory margin, retry
limit and profiling. Tooltips cover speed/memory/quality effects.

OOM retries restart only the failed stage at a smaller batch, up to the configured
limit. Batch-1/model-load/non-OOM failures are reported, not converted into another
model or hidden CPU run. Thermal warnings require at least five thermal-flagged
observations in a ten-sample window, with a 60-second log cooldown. No arbitrary
temperature throttling or unsupported instantaneous “GPU-bound” label was added.

## 9. GPU Configuration Recommendations

All rows use large-v3, beam 5, words on, one worker and sequential GPU stages.
Four CPU threads is a starting value, not a GPU-derived optimum. Unknown devices
are resolved from installed capabilities, not a hard-coded product-name table.

| GPU / capacity | Evidence | Compute / optional ASR batch | Residency / tradeoff |
|---|---|---|---|
| GTX 1060 Laptop 6 GB, Pascal | RESEARCH-BACKED precision; ESTIMATED fit | Supported `int8_float32`; sequential first, batch 2 experimental | Stage residency; diarization 4–8 as a candidate; no measured speed |
| RTX 3080 Laptop 8 GB | MEASURED on this source | `int8_float16`; sequential or optional 4 | Keep, diarization 32 with allocator guard; 8 only prefix-tested |
| Other Ampere/Ada 8 GB | RESEARCH-BACKED / ESTIMATED | Mixed INT8/FP16; explore 2–4 | Validate peaks; stage under pressure |

| 16 GB GPUs / RTX 4090 Laptop | ESTIMATED tuning | Compare supported FP16/INT8; explore 8–16 | Dual residency; laptop power still matters |
| 24 GB / RTX 4090 desktop | ESTIMATED tuning | Explore 8–16, then 32 experimentally | More capacity is not proof concurrency helps |

Use ≥1 GiB margin initially and validate under sustained load; higher tiers can
start at an estimated 15% headroom. RTX 3060 Laptop is normally 6 GB, 4070 Laptop
8 GB, and 4090 Laptop 16 GB—not their desktop capacities. Full sourced rationale:

## 10. Audio Cache and Storage

Existing layout is retained: configured output directory holds transcripts and
queue subfolders; `<cache>/<video_id>` holds source audio, 16 kHz WAV, stage JSON,
per-video labels and ≤5-second speaker samples. Settings exposes both paths and
folder-opening actions; completed rows can open their specific audio/cache folder.

Delete-after-video removes owned audio only after success. Delete-after-queue
removes audio for successful items when that queue drains. Keep-forever bypasses
audio deletion. Failed/cancelled/interrupted downloads and their partial data are
retained for retry; this is intentional storage, not automatically discarded.
Pause itself deletes nothing. A clean close requeues the interrupted stage;
crash recovery resumes from valid saved artifacts. Known unfinished temporary
artifacts are removed on the next processing attempt, not by broad wildcard deletion.

Stage JSON and samples persist for offline editing; a completed cache can re-export
without re-downloading deleted audio. “Reprocess” continues to reuse valid cached
stages—changing settings alone does not invalidate existing ASR/diarization.
Opt-in diagnostic traces are retained separately and can accumulate; disable
profiling for normal bulk use and remove unwanted traces while idle. No user
audio, production caches or historical outputs were deleted by this task.

### Reproduction

Use the installed environment and a fresh output path per experiment. Never run
GPU experiments concurrently. Preserve production data; these tools use isolated
roots. The frozen baseline source is commit `d66665c` (copy/archive `ytscribe/`
from that commit into `benchmark/work/baseline/`). Fetch only the benchmark audio
into `benchmark/work/audio/fZZXVNt1gk0` with the existing acquisition module and
convert using `media.to_wav`. The waveform is 16 kHz mono PCM, 1706.20225 seconds.

```powershell
.venv\Scripts\python.exe -m unittest discover -s tests -q
.venv\Scripts\python.exe -m benchmark.acquire --root benchmark/work/audio
.venv\Scripts\python.exe -m benchmark.measure --source-root benchmark/work/baseline --output benchmark/results/new-baseline --diarize --repeats 2
.venv\Scripts\python.exe -m benchmark.measure --output benchmark/results/new-batch4 --batch 4 --diarize --repeats 2
.venv\Scripts\python.exe -m benchmark.matrix benchmark/results/new-matrix
.venv\Scripts\python.exe -m benchmark.lifecycle prepare --root benchmark/work/new-lifecycle
.venv\Scripts\python.exe -m benchmark.endurance --root benchmark/work/new-lifecycle
.venv\Scripts\python.exe -m benchmark.measure --output benchmark/results/new-oom --only-diarize --duration 300 --margin 6000
.venv\Scripts\python.exe -m benchmark.gui_smoke --probe
```

The 6000 MiB margin is a deliberate **test restriction**, not recommended settings.
The benchmark recorder samples at 0.5 s; UI defaults to 1 s. WER normalizes case,
punctuation and links, excludes reference turns cut by a crop, and never conditions
inference. Reference coverage ends at 1672 s; the source continues to 1706.202 s.
Whole-second reference timestamps and interjections prevent a defensible precise
DER/word-boundary accuracy claim. Early trace timers had ~16 ms granularity;
final recorder uses monotonic high-resolution `perf_counter`.

## 12. Remaining Limitations

**Release scope clarified at handoff:** the 866 queued videos are the user's
production workload, not a test suite. Only the available RTX 3080 Laptop is
required for measured validation. Implementation and the agreed bounded local
verification are complete; the limitations below are disclosures, not pending
release gates. No further bulk run or additional GPU is required to wrap up.

- **UNVERIFIED hardware:** no GTX 1060, 12/16/24/32 GB GPUs or Blackwell machine
  available or expected. Recommendations for them remain research-based or
  estimated, not measured tier/OOM boundaries. No additional hardware is required
  for this release.
- **UNVERIFIED multi-day/corpus behavior:** only the approved benchmark source was
  processed, with repeated full runs and three excerpts. The production queue
  was untouched. This bounded validation does not establish multi-day or
  866-video stability, and that workload is not a release test requirement.
- **UNVERIFIED general quality:** batching changes faster-whisper fallback/VAD/
  decoding behavior. Need diverse held-out transcripts and word-level speaker
  timing for general WER/DER/hallucination guarantees. Defaults remain unchanged.
- **UNVERIFIED exact low-level cause:** allocator counters strongly support the
  restart fix, but no kernel/workspace trace or physical WDDM paging trace was
  collected. Power-limit/Dynamic Boost/fan telemetry was unavailable. No arbitrary
  driver or power tuning was applied.
- **UNVERIFIED fresh-machine installation:** the existing Windows environment was
  exercised; no clean Windows VM/device or new standalone installer was tested.
  Existing setup/launch workflow remains, documented with measured versions.
- Resource safety is bounded, not infallible: model loading and non-PyTorch CUDA
  allocations can still fail; batch 1 may not fit. Errors are surfaced with cache
  preserved. Optional traces and retained failed-job audio require periodic review.
