# YTScribe v0.3: independent library and hardware research

Research date: 2026-09-18. Scope: official upstream sources and read-only inspection; **no inference, benchmarks, GPU probes, or dependency changes performed**. The parent task owns experiments and implementation. Only this new file is authored by this workstream.

Evidence labels: **RESEARCH-BACKED** = official documentation/source; **INFERRED** = code inspection or explicit reasoning; **ESTIMATED** = proposed tuning values, not validated capacity; **EXPERIMENTAL** = requires compatibility/quality testing; **REPORTED** = historical/user claim. There are **no MEASURED performance results** here.

Read the supplied v0.3 request, `DESIGN.md`, relevant historical passages, application ASR/diarization/CUDA wrappers, and installed library code. Installed distribution metadata: faster-whisper **1.2.1**, CTranslate2 **4.8.1**, pyannote.audio **4.0.7**, torch **2.12.1+cu126**. These are filesystem observations, not proof that any particular execution used these packages. Application observations below describe the initial inspected code; the parent is editing concurrently.

## Recommendations for the parent

1. Preserve large-v3, beam 5, word timestamps, and the sequential path as the accuracy baseline. Evaluate batched decoding as a separate inference mode before promoting it into a preset.
2. First compare sequential versus **batched batch 1** to identify semantic changes; then compare batched 1/2/4/8 with identical batched settings to isolate batch-size effects. Keep timestamp and speaker-attribution checks.
3. Select precision from the installed CT2 supported-type set and log the model's resolved `compute_type`. Combine this with free VRAM, loaded-model residency, and library compatibility; product names and total VRAM are insufficient.
4. Keep one GPU job/CT2 worker initially. Tune pyannote segmentation and embedding batches independently. Retain both models only when measured peaks leave headroom.
5. Treat every tier/batch number below as a starting hypothesis. Parent measurements on the RTX 3080 **Laptop 8 GB** supersede these estimates; they do not validate other GPUs.

## faster-whisper: batching changes behavior

**RESEARCH-BACKED / INFERRED**, installed `faster_whisper/transcribe.py` and the [official v1.2.1 source](https://github.com/SYSTRAN/faster-whisper/blob/v1.2.1/faster_whisper/transcribe.py):

| Setting/behavior | Sequential `WhisperModel.transcribe` | `BatchedInferencePipeline.transcribe` |
|---|---|---|
| Previous text | Configurable; YTScribe already disables it | Forced off |
| Temperature | Can retry using the temperature schedule | Uses first temperature only |
| Failure/silence heuristics | Uses compression/log-probability fallback and no-speech rejection | Threshold arguments documented unused; returning `no_speech_prob` does not imply rejection |
| Timestamp tokens | `without_timestamps=False` default | `without_timestamps=True` default; word alignment remains separately available |
| VAD | Off by library default; YTScribe enables it | On by default |
| Long input without VAD | Supported | Requires explicit clips when duration is at least `chunk_length` |
| Clip format | Flat start/end seconds | List of start/end dictionaries in seconds |

**INFERRED, local implementation details:** batched VAD defaults to 160 ms minimum silence and caps speech duration at the chunk length; sequential `VadOptions` defaults to 2000 ms and unlimited speech duration before normal windowing. Merely passing `vad_filter=True` to both does not match segmentation. A supplied VAD dictionary is mutated by the batched path when removing `max_speech_duration_s`; pass a copy. Explicit clips longer than 30 seconds trigger a warning that only the first 30 seconds are transcribed. Keep chunks at or below 30 seconds and preserve restoration to original audio time. See also [official VAD defaults](https://github.com/SYSTRAN/faster-whisper/blob/v1.2.1/faster_whisper/vad.py).

**INFERRED, integration risks:** batching creates features for all chunks before returning its segment generator, so smaller GPU batches do not bound host RAM for long recordings. Time the full call **and complete generator consumption**; separating preprocessing and generation is useful, but timing generator creation alone misses work. `last_speech_timestamp` is wrapper state reset after normal generator exhaustion, not in a `finally` block. Cancellation/OOM can bypass reset. A fresh lightweight batched wrapper per job/retry around the existing Whisper model avoids carrying that state into another file. Do not share a wrapper between concurrent jobs.

**RESEARCH-BACKED:** CT2 defines beam 1 as greedy search and provides a separate `align` operation. **INFERRED:** reducing beam 5 to 1 reduces search work but can change recognized words; it is neither guaranteed faster by a fixed factor nor guaranteed equally accurate. Installed word-timestamp code calls `model.align` and then performs word grouping and boundary processing. Disabling this measures an ASR component cost, but is not an acceptable production optimization for YTScribe's word-to-speaker merge. No universal percentage overhead or millisecond accuracy guarantee is established. [CT2 Whisper API](https://opennmt.net/CTranslate2/python/ctranslate2.models.Whisper.html).

Use a fixed language only when known. Offer model alternatives explicitly: [large-v3-turbo](https://huggingface.co/openai/whisper-large-v3-turbo) reduces decoder layers from 32 to 4; [distil-large-v3](https://huggingface.co/distil-whisper/distil-large-v3) targets English recognition. Their published speed/quality comparisons are workload-specific, not YTScribe measurements.

## CT2 precision, threads, and compatibility

**RESEARCH-BACKED:** the [quantization capability table](https://opennmt.net/CTranslate2/quantization.html) distinguishes Pascal CC 6.1 from CC >= 7 and >= 8. On CC 6.1 the optimized INT8 form is `int8_float32`; `int8_float16` falls back to it in the documented implicit conversion table, and FP16 falls back to FP32. Explicit unsupported selections may fail rather than supply the intended precision. For Ampere/Ada, evaluate `int8_float16` and `float16`; BF16 support alone is no reason to prefer it for Whisper. `int8` is not necessarily the same nonquantized precision across models/devices. Query [get_supported_compute_types](https://opennmt.net/CTranslate2/python/ctranslate2.get_supported_compute_types.html), then record the actual loaded model type. Do not force inefficient FP16 on Pascal through environment overrides.

**RESEARCH-BACKED, version-sensitive Blackwell correction:** CT2 4.6.2 disabled INT8 for sm120. [PR #1982](https://github.com/OpenNMT/CTranslate2/pull/1982) re-enabled it, included in [4.7.0](https://github.com/OpenNMT/CTranslate2/blob/v4.8.1/CHANGELOG.md); [4.8.1 capability code](https://github.com/OpenNMT/CTranslate2/blob/v4.8.1/src/cuda/utils.cc) includes CC 12 in its INT8 predicate. Therefore neither “Blackwell cannot run CT2 INT8” nor “all older CT2 installations support it” is safe. Hardware support, compiled kernels, CUDA DLLs, and actual model execution are separate checks. FP8/FP4 marketing capability does not create a supported faster-whisper `compute_type`.

**RESEARCH-BACKED:** [PyTorch 2.12 release guidance](https://pytorch.org/blog/pytorch-2-12-release-blog/) recommends CUDA 12.6 wheels for legacy architectures and CUDA 13.0+ wheels for Blackwell; the latter requires Windows driver >= 580.88. The inspected `+cu126` environment must not be advertised as a Blackwell-ready installer. Historical driver 581.80 is a REPORTED value, not a current probe. Also validate CT2's own CUDA dependencies: YTScribe currently searches `torch/lib`, so changing PyTorch can change the DLLs available to CT2. A CUDA 13 PyTorch wheel is not proof that a CT2 build's CUDA 12 DLL requirements are satisfied. CT2 4.6.3 also made cuDNN optional through a CUDA convolution implementation; avoid repeating the faster-whisper README's older mandatory-cuDNN statement as universal for CT2 4.8.1. [Versioned changelog](https://github.com/OpenNMT/CTranslate2/blob/v4.8.1/CHANGELOG.md).

**RESEARCH-BACKED:** faster-whisper maps `cpu_threads` to CT2 `intra_threads`, and `num_workers` to `inter_threads`. Multiple workers need concurrent submissions to do useful concurrent work; increasing them does not batch a single sequential generator. CT2 documents shared weights on one GPU, but extra execution resources can still increase memory. Avoid `inter_threads * intra_threads` exceeding physical CPU cores. [Parallelism](https://opennmt.net/CTranslate2/parallel.html), [performance guidance](https://opennmt.net/CTranslate2/performance.html).

**ESTIMATED tuning policy:** start with one worker and the library CPU-thread default (`cpu_threads=0`, documented default 4). Parent may compare 2/4/8 threads, capped to available physical cores and allowing room for the UI/prefetcher. These threads are not a general control for NumPy, PyTorch, PyAV, or VAD. Low aggregate CPU usage cannot rule out a limiting core. No universally ideal count follows from GPU VRAM.

## pyannote batches and memory ownership

**RESEARCH-BACKED:** installed pyannote exposes writable `pipeline.segmentation_batch_size` and `pipeline.embedding_batch_size`; constructor defaults are 1 each, but downloaded pipeline configuration may override them. Record values **after loading**, then change these attributes, not arbitrary call-time `batch_size` kwargs. Segmentation's property updates its inference batch; embedding batch controls embedding grouping. Keep the pretrained segmentation step, clustering configuration, and overlap policy while tuning batches. Preserve `speaker_embeddings` and its mapping to `speaker_diarization.labels()` for voice recognition. [Official 4.0.7 diarization source](https://github.com/pyannote/pyannote-audio/blob/4.0.7/src/pyannote/audio/pipelines/speaker_diarization.py).

**RESEARCH-BACKED:** known `num_speakers` or bounds are supported, as are in-memory waveform input and exclusive diarization. Exclusive output simplifies reconciliation; it does not certify ASR word-boundary accuracy. [Official community-1 model card](https://huggingface.co/pyannote/speaker-diarization-community-1).

**RESEARCH-BACKED / INFERRED:** `pipeline.to(torch.device('cpu'))` moves registered components to CPU, trading GPU residency for RAM and transfer time. Drop remaining live GPU tensors/output references before expecting release. PyTorch allocated bytes describe live tensors; reserved bytes also include reusable allocator blocks. `empty_cache()` releases unused PyTorch cache, not live tensors or CT2's allocator. Call it, if justified, at ownership transitions or after releasing a failed attempt, not reflexively every segment. [Pipeline device transfer](https://github.com/pyannote/pyannote-audio/blob/4.0.7/src/pyannote/audio/core/pipeline.py), [PyTorch memory semantics](https://docs.pytorch.org/docs/2.12/notes/cuda.html#memory-management).

CT2 has its own [caching allocators](https://opennmt.net/CTranslate2/environment_variables.html#ct2-cuda-allocator) and Whisper `unload_model(to_cpu=True)` / `load_model()` APIs. Unloading preserves some runtime context; do not promise zero driver-reported VRAM. Destroying a CUDA context releases its resources; objects from an exited application do not survive into its new process. Compare PIDs and driver-wide memory alongside framework metrics. A fresh-process plateau can be new allocations, other processes, or context overhead; one high VRAM sample cannot identify a leak. [CT2 lifecycle API](https://opennmt.net/CTranslate2/python/ctranslate2.models.Whisper.html), [CUDA context lifecycle](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__CTX.html).

**ESTIMATED retry policy:** on an identified OOM, release the failed iterator/temporary references, halve the relevant batch, and retry the stage with a bounded count and a minimum of 1. Do not append a retried stage to partial output. If batch 1 cannot fit, consider stage-exclusive residency or CPU execution; model substitution requires an explicit profile choice. Separate ASR and diarization retries and do not disguise DLL/unsupported-precision errors as OOM.

**ESTIMATED headroom:** initially target unused VRAM of `max(1 GiB, 15% of total)` at the measured stage peak, including the other resident model and desktop/other-process occupancy. This is an engineering margin, not an upstream requirement or a fit guarantee. Start laptops at the lower batch candidate; record AC/power mode, sustained clocks, temperature, power, and throttling. Capacity checks must precede aggressive batches, but cannot prevent every allocation failure. Exact OOM boundaries depend on chunk/beam/alignment workload, precision, live models, allocator pools, and other applications; none are known from this research. Do not predict realtime multipliers from CUDA cores, AI TOPS, or VRAM.
